## Findings

1. **High — Auth callback permits an external redirect**

   [route.ts](/C:/Projects/naano-rebuild/src/app/auth/callback/route.ts:8) accepts any `next` value beginning with `/`. A value such as `//evil.example` passes that check, and `new URL(nextPath, request.url)` resolves it to an external host after authentication.

   Restrict this to genuine application-relative paths or a route allowlist before enabling the flow publicly.

2. **High — Collaboration write separation is conventional, not enforced**

   [browser-database.ts](/C:/Projects/naano-rebuild/src/types/browser-database.ts:3) makes collaboration inserts and updates TypeScript errors, but that protection can be bypassed with a raw Supabase client, a cast, direct REST calls, or JavaScript. It also does not remove Supabase’s `.delete()` method.

   More importantly, the database explicitly permits client collaboration writes in [schema.sql](/C:/Projects/naano-rebuild/planning/schema.sql:743):

   - Workspace members may insert collaborations.
   - Workspace members may update every column.
   - Creators may update every column as long as `creator_id` remains theirs.

   That lets clients directly manipulate fields such as status, current/accepted offer pointers, identity fields, and soft deletion. This conflicts with the stated rule that collaboration writes must use privileged server commands.

   Money writes are stronger: wallet transactions, holds, and payouts have no client write policies, so those are genuinely server-written at the database level.

3. **High before privileged features — The service-role seam prevents bundling, but not misuse**

   [admin.ts](/C:/Projects/naano-rebuild/src/lib/supabase/admin.ts:1) correctly uses `server-only`, keeps the secret out of the browser, and disables session persistence. However, any server module can obtain the unrestricted service-role client. Nothing ensures that a caller:

   - authenticated the requesting user;
   - checked workspace membership and role;
   - validated the transition;
   - reserved funds before changing collaboration state.

   A Server Action or Route Handler is still a callable endpoint and must perform authorization itself; running on the server is not authorization. [Next.js recommends centralizing these checks in a data-access layer](https://nextjs.org/docs/app/guides/authentication).

   This is presently a readiness gap rather than an exploitable endpoint because no privileged mutations have been implemented yet.

4. **Medium — Signup creates an auth user but not an application identity**

   [actions.ts](/C:/Projects/naano-rebuild/src/app/auth/actions.ts:21) calls `auth.signUp`, but there is no trigger or server workflow creating the corresponding `profiles` row required by [schema.sql](/C:/Projects/naano-rebuild/planning/schema.sql:38).

   There is also no brand-versus-creator onboarding decision or creation of a creator/workspace record. A successfully authenticated new user therefore cannot safely enter the product model without additional bootstrap logic.

5. **Medium — The confirmation/OAuth path is only half-connected**

   The callback correctly uses `exchangeCodeForSession`, but nothing currently sends users to it:

   - `signUp` does not specify `emailRedirectTo`.
   - There is no OAuth sign-in action.
   - No OAuth provider is enabled.
   - Local email confirmation is disabled.
   - The action result cannot distinguish “signed in” from “account created; check your email.”

   This will look successful locally while behaving differently when email confirmation is enabled in development or production. Supabase requires redirect destinations to match its configured allowlist. [Supabase password-auth guidance](https://supabase.com/docs/guides/auth/passwords)

6. **Medium — Redirect configuration is inconsistent**

   [config.toml](/C:/Projects/naano-rebuild/supabase/config.toml:158) uses:

   - Site URL: `http://127.0.0.1:3000`
   - Additional redirect: `https://127.0.0.1:3000`

   The protocol mismatch makes the additional entry ineffective for the local HTTP app, and the callback path is not explicitly allowlisted. Production and preview URLs are also not represented yet. [Supabase redirect URL configuration](https://supabase.com/docs/guides/auth/redirect-urls)

7. **Medium — There is no reusable authorization interface yet**

   The normal server client correctly uses the anon key and request cookies, but there is no `requireUser`, `requireWorkspaceMember`, or role-checking module. Future features would need to repeat security-sensitive logic before using the service role.

   The proxy should not be used as the sole authorization layer, so this absence is not a proxy defect—it is a missing application authorization seam.

8. **Low — Cookie-write failures can be silently swallowed**

   [server.ts](/C:/Projects/naano-rebuild/src/lib/supabase/server.ts:23) catches every error from `cookieStore.set`. Ignoring that failure is expected in Server Components, where cookies cannot be written, but the same factory is used in Server Actions and Route Handlers where failure could indicate a real problem. Authentication could report success without persisting its refreshed session.

9. **Low — No automated guardrails verify the security assumptions**

   There are currently no tests covering:

   - the callback redirect;
   - session cookie refresh;
   - confirmed versus unconfirmed signup;
   - profile bootstrap;
   - browser rejection of privileged writes;
   - service-role authorization.

   ESLint also has no restricted-import rule preventing feature code from importing the admin client or constructing another Supabase client.

## What is correct

The SSR mechanics themselves match Supabase’s current pattern:

- Separate browser and cookie-aware server clients.
- `proxy.ts`, which is the correct filename in Next.js 16.
- Proxy calls `getClaims()` rather than trusting `getSession()`.
- Refreshed cookies are copied to both the request and response.
- Static assets are excluded from the matcher.
- The normal server client uses the anon key, so RLS remains active.

That aligns with [Supabase’s SSR client and proxy guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client). The proxy refreshes authentication; it deliberately does not authorize routes.

Known placeholders are the null home page, empty seed file, unused browser/admin client factories, absent OAuth/reset-password flows, absent privileged mutation modules, and absent auth tests. These are reasonable scaffold placeholders, but the first three high-severity findings should be resolved before feature code relies on the current separation.
